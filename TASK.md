# Домашнее задание №1: «5 букв»

## 1. Подготовка проекта и команды

Для работы понадобятся:

- Go 1.26.0 или новее в пределах ветки 1.26
- GNU Make - необязательно, все команды можно выполнить напрямую

`golangci-lint` зафиксирован в `go.mod` как локальный инструмент и запускается через `go tool`.
Дополнительные конвертеры отчетов, нужные только GitLab, загружаются внутри CI и не требуются
для локальной работы.

Скачайте зависимости:

```bash
make install
```

Команды проекта:

| Команда                | Назначение                                                                               |
| ----------------------------- | -------------------------------------------------------------------------------------------------- |
| `make install`              | Скачать зависимости приложения и локальный линтер      |
| `make build`                | Собрать исполняемый файл в каталоге`bin`                          |
| `make run`                  | Запустить приложение                                                            |
| `make run ARGS="--seed 42"` | Запустить приложение с аргументами                                  |
| `make format`               | Отформатировать код через gofumpt и goimports                              |
| `make test`                 | Запустить`go test` и создать HTML-отчет покрытия                   |

Готовых тестов в шаблоне нет: напишите их самостоятельно. В отличие от pytest, команда `go test`
успешно завершается для пакета без `_test.go`, поэтому зеленый стартовый pipeline еще не означает,
что требования покрыты тестами.

## 2. Описание

Разработайте консольную игру в духе Wordle. Программа загадывает слово из пяти русских букв,
а игрок должен угадать его за шесть попыток.

После каждой принятой попытки программа отмечает каждую букву:

- ✅ - буква стоит на своем месте.
- 🟡 - буква есть в ответе, но стоит в другом месте.
- ❌ - неиспользованной такой буквы в ответе нет.

Пример:

```text
Загадано:  озеро
Ввод:      арбуз
Результат: ❌🟡❌❌🟡
```

Геймификация используется в финтехе, образовательных продуктах и маркетплейсах: ежедневные
задания, стрики, бейджи, викторины и промо-игры повышают вовлеченность пользователей. В этом
задании на небольшой механике отрабатываются типичные инженерные задачи:

- Доменная модель и ее инварианты.
- Разделение бизнес-логики и консольного ввода-вывода.
- Валидация на границе системы.
- Воспроизводимая случайность через seed.
- Тестирование поведения и крайних случае.
- Разработка небольшими осмысленными MR (merge request).

## 3. Требования к реализации

Точка входа CLI находится в `cmd/fiveletters/main.go`, как принято для исполняемых приложений
в Go. Остальная структура решения не задается. Если точка входа или команды меняются, обновите
Makefile и GitLab CI.

Начальный публичный контракт:

```go
type GameSession struct { /* поля определите самостоятельно */ }
type GuessResult struct { /* поля определите самостоятельно */ }

func StartGame(dictionary []string, maxAttempts int, seed int64) (GameSession, error)
func ApplyGuess(session *GameSession, guess string) (GuessResult, error)
```

Внутреннее устройство моделей, дополнительные типы и разбиение по файлам определите самостоятельно.

Обязательные свойства решения:

- консольный слой отвечает только за чтение ввода, вызов игровой логики и вывод результата
- игровая логика не читает `os.Stdin` и не пишет в `os.Stdout` или `os.Stderr`
  (это делается отдельно от игровой логики)
- зависимости консольного слоя от ввода и вывода передаются как `io.Reader` и `io.Writer`
- некорректный ввод возвращает ожидаемую ошибку, не меняет сессию и не расходует попытку
- завершенная игра не принимает новые попытки
- одинаковые словарь, `maxAttempts` и seed дают одинаковый ответ
- `maxAttempts` должен быть больше нуля
- ответ принадлежит словарю и состоит ровно из пяти русских букв
- состояние, история, число использованных попыток и статус не противоречат друг другу
- ожидаемые ошибки ввода возвращаются вызывающему коду, а не приводят к `panic`

Go хранит строки в UTF-8, поэтому `len(word)` возвращает число байт, а не букв.

Для статуса игры заведите отдельный тип и именованные константы `IN_PROGRESS`, `WIN`, `LOSE`.
Названия Go-идентификаторов оформите по правилам языка, например `StatusInProgress`.

Для случайного выбора используйте отдельный локальный генератор, созданный из seed. Не меняйте
глобальное состояние генератора. Не собирайте итоговый словарь обходом `map`: порядок обхода map
не определен и разрушит воспроизводимость.

## 4. Merge request

При создании MR выберите шаблон [`requirements`](.gitlab/merge_request_templates/requirements.md).
В нем уже находится чек-лист для проверки работы.

### MR1 - данные и игровая сессия

- Словарь минимум из 50 уникальных пятибуквенных русских слов.
- Ошибка для пустого или некорректного словаря.
- Случайный выбор ответа с фиксируемым seed.
- `GameSession` с ответом, максимальным числом попыток, числом использованных попыток,
  историей попыток и статусом.
- `StartGame(dictionary, maxAttempts, seed)`.
- Проверка инвариантов сессии.

### MR2 - правила игры

Реализуйте `ApplyGuess(session, guess)` и проверку букв.

- Ввод обрабатывается без учета регистра.
- Допустимы только русские буквы и ровно пять букв.
- Попытка должна находиться в словаре (ввод должен быть настоящим словом из набора допустимых слов игры).
- Некорректная попытка не меняет сессию.
- Результат содержит пять отметок ✅, 🟡 или ❌.
- Правильный ответ переводит игру в `WIN`.
- Последняя неправильная попытка переводит игру в `LOSE`.

Главная ловушка - повторяющиеся буквы. Каждая буква ответа расходуется один раз: сначала
отметьте все точные совпадения ✅, затем оставшимися буквами ответа закройте 🟡.

```text
Загадано:                   отбор
Ввод:                       около
Правильный вывод программы: ✅❌🟡❌❌
```

### MR3 - консольный интерфейс и проверяемость

- Меню: новая игра / выход.
- Возможность сыграть несколько игр без перезапуска программы.
- Устойчивость к некорректным пунктам меню и пользовательскому вводу.
- Отображение истории и количества оставшихся попыток.
- Детерминированный режим для проверки.

Реализуйте хотя бы один вариант детерминированного запуска:

- аргумент `--seed N`
- явно заданный ответ
- команда `check --answer WORD --guess WORD`

Формат сообщений должен быть фиксированным:

- `❌🟡❌❌🟡 арбуз`
- `Осталось попыток: 5`
- `Победа! Слово угадано за 4 попытки`
- `Неудача. Загаданное слово: озеро`

## 5. Тесты

Используйте стандартный пакет `testing`. Тесты размещаются рядом с проверяемым кодом в файлах
`*_test.go`. Пишите табличные тесты и именованные сценарии через `t.Run`.

Проверьте:

- словарь содержит не менее 50 уникальных слов, каждое слово состоит ровно из пяти букв
- пустой или некорректный словарь приводит к ошибке
- при одинаковом seed из одинакового словаря выбирается одинаковый ответ
- слово с неверной длиной, цифрами или специальными символами отклоняется
- слово, которого нет в словаре допустимых слов, отклоняется
- отклоненная попытка не расходует ход и не изменяет состояние игры
- отметки ✅, 🟡 и ❌ правильно расставляются в базовом случае
- для ответа `отбор` и попытки `около` получается `✅❌🟡❌❌`
- регистр введенного слова не влияет на результат
- правильный ответ завершает игру со статусом `WIN`
- после шести неправильных попыток игра завершается со статусом `LOSE` и показывает ответ
- завершенная игра не принимает новые попытки
- некорректный пункт меню не приводит к падению программы
- без перезапуска программы можно сыграть несколько игр
- детерминированный режим возвращает результат в установленном формате

Для проверок консольного слоя используйте `strings.Reader`, `bytes.Buffer` или отдельный процесс.
Основную игровую логику тестируйте напрямую, не ограничивайтесь одним blackbox-тестом программы.
Не сравнивайте ошибки только по тексту, если их можно представить sentinel-ошибками и проверить
через `errors.Is`.

Команда `make test` запускает стандартный `go test` и формирует:

- `coverage.out` с профилем покрытия
- `coverage.html` для просмотра в браузере

`make test-race` отдельно включает race detector. Для него локально нужен Go с поддержкой CGO и
C-компилятор.

## 6. Ограничения и советы

Ограничения:

- используйте стандартный текстовый ввод и вывод
- не добавляйте GUI, веб-интерфейс или сетевой сервис
- игра работает только со словами из пяти букв
- не загружайте словари из внешних сервисов
- не используйте внешние библиотеки для реализации правил игры и управления ее состоянием

Советы:

- не реализуйте всю игру в одной большой функции
- отделите правила игры от интерактивного консольного интерфейса
- не создавайте интерфейсы заранее - вводите их в месте использования, когда появляется реальная
  необходимость подменить зависимость
- не используйте глобальные изменяемые переменные для словаря, сессии и генератора
- возвращайте ошибки для ожидаемых проблем и добавляйте к ним контекст через `%w`
- нормализуйте и проверяйте слово в одном месте
- копируйте входной словарь, если сессия не должна зависеть от последующих изменений слайса
- сортируйте данные явно, если порядок влияет на вывод или воспроизводимость
- используйте `t.Helper()` для вспомогательных функций тестов
- запускайте отдельные сценарии через `go test -run` во время разработки
- регулярно выполняйте `make format`, `make check` и `make test`
